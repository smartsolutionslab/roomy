# 0034. Wolverine runs from pre-generated (static) code, not a runtime compiler

- **Status:** Proposed
- **Date:** 2026-06-09
- **Deciders:** Heiko Weiß

## Context and problem statement

Wolverine generates a handler/middleware wrapper class per message at startup. Historically
it compiled that code at runtime with Roslyn. **WolverineFx 6.5 removed the runtime compiler
from the core package** (GH-2876): a host running in the default `TypeLoadMode.Dynamic` now
throws on startup unless it either references `WolverineFx.RuntimeCompilation` *or* runs from
code generated ahead of time.

`apps/identity-api` did neither, so it **crashed at boot**:

> Wolverine is running in TypeLoadMode.Dynamic … but no IAssemblyGenerator (Roslyn) is
> registered. Core WolverineFx no longer ships the runtime compiler.

The crash surfaced as a "messaging/RabbitMQ" failure because it is the Wolverine messaging
runtime that fails to start — not the broker (RabbitMQ was healthy). The existing messaging
tests did not catch it: the in-memory harness tests reference `WolverineFx.RuntimeCompilation`
themselves, and no test starts a production host's Wolverine runtime. A comment in the test
project even named the intended production approach — *"production hosts pre-generate code via
the Wolverine codegen command"* — but that was never implemented.

## Decision drivers

- **Stop the crash** and keep every messaging host starting reliably.
- **No Roslyn at runtime in production** — smaller images, faster cold start, and trim/AOT
  friendliness (ADR-0017 targets Linux containers). This is the option the project already
  intended.
- **Simplicity / one place for the policy** — Wolverine is wired in exactly one composition
  point (`AddRoomyMessaging`, ADR-0005); the codegen policy belongs there, not copied per host.
- **Context isolation** — the shared messaging library must not reference any context's types.
- **Drift safety** — pre-generated code that silently goes stale is a latent bug; a changed
  handler with un-regenerated code must fail the build, not production.

## Considered options

- **A — Runtime compilation.** Reference `WolverineFx.RuntimeCompilation` in every host so
  Wolverine compiles handler code at startup. Simplest, but ships Roslyn into every runtime
  image (slower cold start, not AOT) — the opposite of the project's stated intent.
- **B — Static code generation (chosen).** Set `TypeLoadMode.Static`; each host commits the
  output of `dotnet run -- codegen write` and loads it at runtime. No runtime compiler. Costs a
  regeneration step when handlers/Wolverine config change, guarded by `codegen verify` in CI.

## Decision

We chose **Option B**. In the shared `AddRoomyMessaging` (`infrastructure-messaging`):

- `wolverine.CodeGeneration.TypeLoadMode = TypeLoadMode.Static` — load pre-generated types,
  never compile at runtime.
- `wolverine.ServiceLocationPolicy = ServiceLocationPolicy.AllowedButWarn` — let generated code
  resolve dependencies it cannot construct inline (notably ports registered as typed
  `HttpClient`s — an opaque factory, e.g. the Keycloak-backed `IIdentityProviderPort`) from the
  scoped `IServiceProvider`. This is plain service location, **not** runtime compilation, so the
  no-Roslyn guarantee holds; the warning keeps the trade-off visible.
- The host passes its own assembly as the **application assembly**
  (`applicationAssembly: typeof(IdentityApiHost).Assembly`). Wolverine otherwise defaults the
  application assembly to the caller of `UseWolverine` — this shared library — and would look
  for the pre-generated `HandlerRegistry` in the wrong place (falling back to a scan, then to
  the missing runtime compiler). The generated code is committed in the host project, so the
  application assembly must be the host.

Each messaging host:

- wires the JasperFx command line — `return await app.RunJasperFxCommands(args)` instead of
  `app.Run()` — so `dotnet run -- codegen write` / `codegen verify` are available;
- commits the generated code under `apps/<host>/Internal/Generated/` (marked `generated_code`
  in `.editorconfig`, and already carrying `// <auto-generated/>` + `#pragma warning disable`,
  so analyzers and `dotnet format` leave it alone);
- is guarded by a CI step running `codegen verify`, which fails the build when the committed
  code drifts from what the current handlers/config would generate.

`apps/identity-api` is the only messaging host today; `organization` and `attendance` follow
the same three steps as they land.

## Consequences

**Positive**
- The host boots with no runtime compiler — the crash is fixed, and production images carry no
  Roslyn (faster cold start, AOT-friendly), matching the project's intent.
- The codegen policy lives in one shared place; adding a context is mechanical.
- `codegen verify` turns "stale generated code" from a latent production failure into a
  build failure.

**Negative / trade-offs**
- A handler change or Wolverine-config change requires re-running `codegen write` and
  committing the result; forgetting is caught by CI but is an extra step.
- The committed generated code is noise in diffs and reviews (mitigated: it is clearly
  auto-generated and excluded from analysis/formatting).
- `ServiceLocationPolicy.AllowedButWarn` logs a warning for each service-located dependency at
  startup; accepted as a visible, intentional signal for the typed-HttpClient ports.

**Follow-ups**
- When `organization` / `attendance` gain messaging, wire `RunJasperFxCommands`, set the
  application assembly, commit their generated code, and extend the CI `codegen verify` step.
