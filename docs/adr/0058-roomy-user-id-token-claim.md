# 0058. Carry the Roomy UserIdentifier as a token claim; resolve the current user from it

- **Status:** Accepted
- **Date:** 2026-06-11
- **Deciders:** Heiko Weiß

## Context and problem statement

Every user-scoped endpoint resolves the caller to a domain `UserIdentifier` and looks the
person up by it — `/account` (identity), and `/reservations/mine`, `/reservations` on-behalf,
and the per-employee view (attendance), all via `principal.Subject()` → `UserIdentifier.From(…)`.

`CurrentUser.Subject()` (ADR-0053) read the token's `sub`, on the assumption that the Keycloak
`sub` *is* the Roomy `UserIdentifier`. It is not:

- Roomy mints its own GUIDv7 `UserIdentifier` for each `User`, and **that** value flows through
  `UserRegistered` → the organization `Employee.UserId` → the attendance `employees.user_id`.
- Keycloak mints its **own** random GUIDv4 as the `sub`, and the user is stored with both.
- Keycloak's `POST /admin/realms/{realm}/users` **ignores any supplied `id`** (verified against
  Keycloak 26.6.3 — a requested id is discarded and a fresh UUID returned), so `sub` cannot be
  pinned to the `UserIdentifier` at creation.

Result: `FindByUserAsync(token.sub)` compares a GUIDv4 against the stored GUIDv7 and never
matches — `/reservations/mine` returns `unknown_employee` for **every** user. Role/catalogue
endpoints don't read the subject, so the defect stayed hidden. (A second, prerequisite defect —
the `roomy-bff` client omitted Keycloak's `basic` scope, so tokens carried no `sub` at all — is
fixed separately in the realm import.)

## Decision drivers

- **The GUIDv7 `UserIdentifier` is canonical.** It is generated by Roomy, correlated by the
  account-provisioning saga (ADR-0025), and already keys `User`, `Employee`, and the attendance
  read model. The token must carry *that* identifier, not Keycloak's incidental `sub`.
- **Keycloak owns `sub`.** It cannot be forced to the `UserIdentifier`, so the mapping has to be
  explicit rather than assumed-equal.
- **One seam.** All four call sites already funnel through `CurrentUser.Subject()`; fixing the
  resolution there fixes every endpoint without touching the saga or the GUIDv7 convention.
- **Fail closed.** A token that cannot be mapped to a Roomy user must not silently resolve to a
  wrong/empty identity.

## Considered options

- **A — Make the Keycloak `sub` canonical.** Adopt Keycloak's generated `sub` as the `User`'s
  identifier and propagate it through identity → organization → attendance. Matches the old
  `UserIdentifier.From(sub)` assumption but reworks the registration/saga flow and abandons the
  GUIDv7 convention for `User`. Largest blast radius.
- **B — Carry the Roomy `UserIdentifier` as a token claim (chosen).** Provisioning stores the
  `UserIdentifier` as a Keycloak user attribute; a realm protocol mapper emits it as a
  `roomy_user_id` claim; `CurrentUser.Subject()` reads that claim. Keeps GUIDv7 ids and the saga;
  localized to provisioning, the realm import, and `web-http`.

## Decision

**Option B.** The token carries the Roomy `UserIdentifier` as the `roomy_user_id` claim, and the
API trusts that claim — not `sub` — as the caller's identity.

1. **Claim constant.** `RoomyClaims.UserId = "roomy_user_id"` in `web-http`, beside `RoomyRoles`.
2. **Two distinct reads at the edge.** `CurrentUser` keeps `Subject()` (the Keycloak `sub`, via
   `NameIdentifier ?? "sub"`) and gains `UserId()` (the Roomy `UserIdentifier`, from the
   `roomy_user_id` claim; absent/unparsable → `Error.Unauthorized`). They are different values:
   - **Identity** owns the Keycloak↔Roomy mapping and resolves the account by the Keycloak subject
     (`GetByKeycloakSubjectAsync`), so `/account/me` keeps using `Subject()`.
   - **Attendance** only knows the domain `UserId`, so its three subject reads switch to `UserId()`
     and wrap it as `UserIdentifier`.
3. **Provisioning.** `KeycloakIdentityProvider` (which now receives the `UserIdentifier`) sets the
   Keycloak user attribute `roomy_user_id` to it at creation. Keycloak 26's declarative user
   profile drops unmanaged attributes, so the realm import declares `roomy_user_id` as a managed
   attribute (admin view/edit) via the `UserProfileProvider` component.
4. **Realm import.** The `roomy-bff` client gains an `oidc-usermodel-attribute-mapper` emitting the
   `roomy_user_id` user attribute into the access token, ID token, and UserInfo.

## Consequences

**Positive**
- `/reservations/mine`, `/account`, and on-behalf flows resolve the correct domain user; the
  GUIDv7 `UserIdentifier` stays the single canonical id end to end.
- No saga change and no new cross-context dependency; the fix is confined to the identity edge,
  the realm import, and `web-http`.
- Tokens that lack the claim fail closed at the edge.

**Negative / trade-offs**
- Two edge reads now exist (`Subject()` = Keycloak sub, `UserId()` = Roomy UserIdentifier); callers
  must pick the right one. This refines ADR-0053, which assumed a single subject read.
- Requires a realm re-import (or attribute backfill) and a re-seed; users provisioned before this
  change carry no `roomy_user_id` attribute and cannot be resolved by `UserId()` until reprovisioned.
- `ProvisionUserAsync` gains a `UserIdentifier` parameter (port + all callers/doubles updated).
